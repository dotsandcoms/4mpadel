# Native division-switch top-ups

The entry-management sheet sends higher-priced solo division switches to `/events/switch-division`. The native review shows current and target division fees, the difference, and that a linked partner stays in the original division. Fees match the existing division-switch service's stored division prices. The payment browser opens Paystack checkout, not the 4M website.

`native-division-switch` is deployed with gateway JWT verification disabled because its public GET return route must be callable by the payment browser. Every POST independently verifies the user token. Quotes and initialization require the caller's own paid, active entry, an active target in the same event, no existing target entry, and open event/division deadlines. Price and identifiers are resolved on the server.

The endpoint stores a payment-ledger attempt, uses a deterministic provider reference for concurrent initialization, and resumes pending attempts across screen/app restarts. Initialization and confirmation never trust client prices. The HTTPS return endpoint accepts only a correctly formatted reference and redirects to a fixed `fourmpadel://events/switch-division` route; it does not write data or confirm payment.

Confirmation verifies the exact reference, payer, live mode, ZAR currency and amount with Paystack before forwarding the authenticated caller to the established `paystack-refund` switch action. A conditional payment-metadata claim prevents overlapping native confirmations. The existing service performs the move, unlinking, payment allocation and notifications. Metadata is reread before marking completion so existing service changes are preserved. Completed retries return success without repeating the move. If fees, entry state or deadlines change after payment, the app retains the reference and reports the problem rather than initiating another charge.

On return (including a cold start), the app verifies payment and shows a native success screen with a link to the event. Closing an unpaid checkout leaves the original entry in place and offers resume/check-status controls. Reopening a pending switch verifies it before offering further payment. This flow moves one player; whole-team top-up checkout is not part of this request.

Validation: TypeScript and the existing suite passed. Nine service tests cover pricing, authentication/ownership/deadlines, attempt reuse, pending payments, provider-field validation, reference binding, completion retries, changed pricing/failed moves and a fixed read-only return URL. Four entry-management tests include native top-up navigation. Three screen tests cover pay/verify/navigation, cold return and unpaid status retry. Live probes returned 302 to the app and 401 for an unauthenticated POST. No real payment, registration switch, email or push was generated by these tests. A real paid round trip remains to be verified on the user's phone.

No SQL migration is required; this uses the existing payments ledger and division-switch service. Notification recipient scope is unchanged.
