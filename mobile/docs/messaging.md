# In-app messaging

Implemented for Expo SDK 57 iOS/Android and the shared website Event Management module. The hosted backend was deployed on 5 November 2026 for a restricted staff pilot. Wider player access and junior messaging remain disabled. The first live message and push were confirmed by the recipient. See the deployment record below for the follow-up update and remaining device checks.

## Experience

- The fifth native tab is Messages, with All/Players/Events, Requests, Archived, search and unread message counts. The navigation badge disappears at zero. Long press and the three-dot menu offer Mark as unread; reminders use a separate marker and preserve actual read history. Messaging preferences live under Account & Settings → Messaging.
- Player profiles open an introduction composer. A verified, linked player who has accepted the current rules can send one 300-character request. Further messages require acceptance. Requests are capped at ten per day; declines have a thirty-day cooldown.
- Event messages are reachable from event details and the Messages event directory. Active registrants receive announcements; server-confirmed/free/comped or organiser-approved entrants receive discussion. Both mapped partners are included; spectators and followers are excluded.
- Event discussion begins at the current membership interval. Withdrawal/replacement/rejoining and consent changes reset access correctly. Announcements remain readable to currently active registrants irrespective of when published.
- Text (4,000 code points server-side), emoji, replies, event/Draws/Results cards, pinning, mute, archive, block/unblock, reporting and removal are included. There are no public read receipts, online/last-seen status, uploads, arbitrary groups or calls.
- Organisers use the same API in the app and website, with TOTP MFA required for publishing and moderation. The website composer includes a separate review step before publishing to all active registrants. Event reports and explicit discussion approval are available on both platforms.
- Support can inspect submitted DM report evidence with MFA and an existing super-admin or explicit `messaging-support` permission. It cannot browse unrelated private conversations. Suspension is scoped to the reported sender. Broader unreported-content access has no product endpoint; a separately approved, audited exceptional-access process is required before any such access is introduced.

## Trust and database boundary

`20261105094904_in_app_messaging.sql` creates the non-exposed `messaging` schema. Every table has RLS with no client table policies/grants. `service_role` has explicit CRUD, schema USAGE and identity sequence USAGE. Public entrypoints are SECURITY INVOKER wrappers around private, explicitly granted functions. Internal helper EXECUTE is revoked from clients. Never add this schema to PostgREST/GraphQL exposure or the Postgres Changes publication.

`messaging_api(action, data)` derives identity from `auth.uid()`, checks a real confirmed Auth user, current email, server session and suspension, and links exactly one player. It ignores supplied sender/role/email claims in request data. Table data, Auth identifiers, phone numbers, email addresses, DOB, identity details, guardian email and push tokens are excluded from participant DTOs. Only necessary public player identity, authorised message content and event metadata are returned.

Messaging organisation access requires ownership/admin membership in the event’s organisation, its named organiser/co-admin, an explicit event-ID assignment, or deliberate platform super-admin authority. A generic legacy Full Access sidebar tab is insufficient. Registered players can read their own eligible event channels; this does not grant administrative access to their organisation. Two-organisation integration tests reject cross-event reads, sends, pins and reports.

The legacy `is_super_admin` overloads receive a fixed `pg_catalog,public,pg_temp` path, preserving their logic while making them safe to call from empty-search-path functions. Otherwise their unqualified permissions-table lookup can fail inside the new API.

### Payment integrity

Read-only catalog inspection on 5 November confirmed that authenticated clients have UPDATE privilege for registration payment fields. Messaging therefore does **not** grant discussion solely from a `paid` flag.

`entry_confirmations` contains an identity/payment fingerprint produced only by a trusted service writer, privileged database operation with no caller identity, or verified MFA event manager. A client changing event/email/partner/payment/status fields invalidates that record. Both own and partner payment states require matching attestation. Authoritative imported entries also require a trusted import attestation. Manual discussion approval is a separate, event-scoped MFA operation.

Existing registrations/imports are deliberately not blanket-attested during migration. Reconcile existing entries against verified payment/import records, or explicitly approve eligible entrants through the organiser screen. Never backfill by copying every legacy `paid` flag. Payment and import writers using a service JWT create attestations on subsequent writes. Test the actual production payment and import paths in staging before activation.

### Realtime and delivery

Empty `inbox_changed` signals use private own-account (`messaging:<Auth UUID>`) and authorised conversation (`messaging-thread:<conversation UUID>`) topics. One conversation broadcast replaces per-recipient broadcasts on message creation. Restrictive policies prevent broad legacy policies from allowing cross-account reads or client publication. A topic never transports message content. The app fetches a freshly authorised snapshot; message previews are omitted while outside messaging routes. A foreground banner includes the event title and opens that chat, with no message text in the banner. An already-open chat suppresses its own banner.

Healthy sockets generate no periodic inbox queries. Signals are coalesced, while foreground/navigation refreshes and a jittered, backed-off disconnected-only fallback repair missed updates. There is one inbox snapshot RPC rather than separate status/list calls. Own read/settings changes propagate across devices; announcement read and provider status changes notify the sender dashboard without broadcasting every read to every participant.

The durable private outbox records one job per recipient/device/message, using set-based insertion. Service-only batch RPCs claim up to 200 jobs with fresh access, device ownership, mute/preferences, quiet-hours and expiry checks. The worker sends arrays of at most 100, batches provider receipts and finish operations, and continues bounded draining rather than stopping after 50 jobs. A database budget reserves at most 400 chat jobs/second; the existing one-minute scheduler remains recovery. Push retries and provider delivery can still be delayed or duplicated across a crash; app messages are idempotent.

Event push titles contain the event name, with generic announcement/message copy and an exact `/messages/<UUID>` destination. No message body or player contact data goes to the push provider. Tap routing accepts only an exact allowlisted route; opening the chat performs normal fresh authorization.

App-icon badges combine unread messages with the same missing-region/racket and outstanding-payment actions as Home. The own-only `app-badge` Edge Function validates the current Auth user and live session, accepts no recipient identity from its request, and returns counts only. Pending counts are cached per account, revision-fenced and invalidated by relevant profile/registration/payment/event/division writes. Chat pushes use the last cached Pending count without recalculating financial balances per recipient. Foreground refresh updates dirty counts; background Pending counts can remain last-known until that refresh. Native badge writes are serialized and identity-fenced; zero clears the badge. Android badge display depends on launcher support.

The web dashboard uses an MFA-protected, server-filtered search directory and independently authorised event aggregates. It shows app audience, announcements, aggregate reads, reports and each announcement's queued/accepted/provider-confirmed/failed/skipped device jobs. Read statistics reflect current eligible app audience, not a historical recipient export; provider receipts are not proof that a person read the message. Changing event clears the composer, review, content and statistics before loading the next event.

## Device privacy and juniors

- Native message screens await screen-capture protection before displaying content. Each screen has an independent key; native calls are serialized across navigation. App-switcher protection and background/account-change cleanup are included. Recipients can still photograph or transcribe content.
- Sent messages are held in memory. Drafts alone use account-scoped, chunked SecureStore with `WHEN_UNLOCKED_THIS_DEVICE_ONLY`, a twenty-draft bound and a twenty-four-hour expiry. Sign-out/account switching prevents late writes and clears the index. Web drafts never fall back to unencrypted browser storage.
- Messaging content is not supplied to analytics. Route identifiers and invitation fields are filtered from Observe navigation metrics. API errors are sanitised before display. Chat avatar loads are restricted to the configured Supabase public profile-image origin and bucket; arbitrary external tracking URLs and signed private URLs are rejected. No external URL previews or third-party content scanning are performed. Text is rendered as text in native and React web components.
- DOB uses the existing private profile-details store. Juniors accept the same rules and obtain a separate guardian's consent. A guardian must control the invited verified email, have an adult DOB, make the authority declaration, and have signed in within fifteen minutes. Invitations are high-entropy, hashed at rest, expire after forty-eight hours and are explicitly shared by the junior through the OS share sheet. Consent is versioned and revocable. Mailbox control and declared DOB/authority are not independent proof of guardianship; safeguarding/privacy review is mandatory.
- `juniors_enabled` defaults to false even after adult messaging is enabled. No certification, legal-compliance or absolute secrecy claim is made by this implementation.

## Retention and operations

Calendar and age boundaries use Africa/Johannesburg consistently. DMs expire twelve months after sending. Event content expires ninety days after the final event date; posting closes after seven days and discussion closes immediately on cancellation. Read checks enforce expiry even before cleanup. Own deletion and authorised moderation remove live content immediately, leaving tombstones. Account deletion erases authored bodies/cards/replies before account references disappear. Report evidence is separate, retained 180 days after case closure unless a documented legal hold applies; audit metadata is retained twelve months. The existing worker performs cleanup; monitor its successful execution and backlog.

Backups have their own provider retention. Restore into an isolated, disabled environment, reconcile post-backup account/message erasures from separately retained security records, and complete the privacy review before reopening access. Do not describe live deletion as immediate physical deletion from all backups. Operational backup/restore and independent audit evidence remain release gates.
